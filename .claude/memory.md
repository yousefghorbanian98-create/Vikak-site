## 2026-11-07 · ECC is the only toolchain

**Decision.** The project runs entirely under ECC (`ecc-universal@2.2.3`), installed into
this repository at `.claude/` via:

```bash
npx -y ecc-universal@2.2.3 install \
  --target claude-project --profile minimal \
  --with framework:nextjs --with lang:typescript --with skill:security-review
```

Install-state: `.claude/ecc/install-state.json` (schema `ecc.install.v1`).
Result: 137 skills, 94 commands, 68 agents, 23 rule packs, 4 helper scripts.

**Removed.** Five third-party skill bundles (`taste`, `finn-build`, `finn-spec`,
`ui-ux-pro-max`, `design-motion-principles`) and their `.gitignore` entries. They
violated the "ECC only" constraint. Their *design outcomes* survive in the code
(design system in `app/globals.css`, motion in `components/reveal.tsx`); the skills
themselves do not.

**Why it was missed.** The first ECC invocation was `plan`, which only prints a mapping
and installs nothing. `install` was required for real.

## 2026-11-08 · install-state: portable on purpose

`ecc doctor` records and compares **absolute** paths, so a state committed from one
machine always warns on another. The committed state is therefore normalized to
project-relative paths (`scripts/normalize-ecc-state.mjs`), which is what makes the
repo usable everywhere.

Consequence, by design:

- In **CI**: check portability -> re-run the pinned `install` (records this runner's
  paths) -> `doctor` is then **OK**. This is also the reproducibility test.
- **Locally**: `doctor` warns about a root mismatch until you run the same `install`.
  That warning is expected. `node scripts/normalize-ecc-state.mjs` before committing.

## 2026-11-07 · Headless WooCommerce backend (option ب)

WooCommerce owns price, stock, cart, Zarinpal payment, weight-based shipping and
invoices. Next.js remains the storefront: SSG + ISR 300 s, 58 static pages, 53 products.
Contract in `docs/HEADLESS.md`; mu-plugin in `wordpress/vikak-headless.php`.

**Hard-won detail.** Next 16 caches a *failed* `fetch` result. `next: { revalidate }` is
not sufficient for an optional backend. `lib/wp.ts` must use `cache: 'no-store'` and let
the page-level ISR handle freshness. Verified by killing the stub backend: the page kept
claiming "live" with stale data until this was changed.

## Known limits (do not paper over)

- PHP was never executed in this environment (`php` is not installed). The mu-plugin was
  only statically checked; real validation needs a WordPress host.
- A mock WordPress stub stood in for a real WooCommerce instance.
- Product images are AI-generated placeholders; imported images point at
  raw.githubusercontent URLs and must be replaced before launch.
- `scripts/consistency.mjs` cannot finish on CPU; `gate.mjs` needs an upstream-missing
  `assets/layout/check.mjs`. Neither is a project gate.
